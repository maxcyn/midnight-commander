1 · Detection with Sentry

Instrumentation (demo app)

  • Errors on failed checkouts
  • Spans: checkout → recommendations → payment
  • Structured logs: dependency outcomes, flag changes
  • Attributes: service, env, release, request & run ID

Alert intake (backend)

  • Verify the webhook's HMAC signature
  • Save, acknowledge fast, process asynchronously
  • Same delivery retried → processed once
  • Same issue + env recurring → attach, don't re-page
  • Open incident, assign primary & backup owner

Output: an incident ID handed to the context agent.

2 · Context agent + incidents.md

Gathers fresh evidence

  • sentry_evidence — errors, logs, spans for the window
  • feature_config — current flags & provider
  • probe — live health of each dependency
  • Every item gets a source_id the backend can check

Recalls similar past issues

  • Parse the table in incidents.md
  • Filter in code: same service / failing stage
  • LLM ranks remaining rows on symptoms + evidence
  • Return top 5 with a one-line "why similar"
| ID    | Date       | Service  | Symptom / error signature              | Failing stage   | Root cause                      | Fix applied              | Outcome   | Follow-up                       |
|-------|------------|----------|----------------------------------------|-----------------|---------------------------------|--------------------------|-----------|---------------------------------|
| INC-7 | 2026-10-12 | checkout | recommendation lookup timed out 800ms  | recommendations | recommendation service outage   | disable_recommendations  | recovered | make checkout tolerate outage   |
| INC-9 | 2026-10-15 | checkout | recommendation timeout, payment slow   | recommendations | payment provider saturating pool| switch_payment_provider  | recovered | isolate connection pools        |

Rules

  • Past issues are guidance, not evidence
  • Similar symptoms ≠ same cause — check what differs now
  • No match → empty list, no invented precedent
  • Agent 1 never proposes; it only assembles context

3 · Recommendation agent + policy gate

Agent output

  • Hypotheses: supported / inconclusive / contradicted — no % confidence
  • Proposed action from the allowed list + tradeoff
  • based_on: which past issue IDs it followed or rejected, and why
  • A short spoken briefing for the call

Backend gate (deterministic)

  • Cited source_ids must exist and be < 15 min old
  • Exactly one supported cause
  • Action on allowlist and matches that cause
  • Target environment = demo
  • Fails → escalate to the SWE with no proposal

The model proposes. The backend decides what may be offered. The human decides what runs.

4 · The phone call — ElevenLabs + Photon

Photon provides the phone number and SIP trunk; ElevenLabs runs the conversation. The voice agent speaks from the same incident record.

SWE saysVoice toolBackend effect
"Explain the evidence"explain_evidenceReads briefing, hypotheses, similar issues
"Yes, do it"approve_actionExecutes the exact pending action
"No" / "I'll handle it"decline_actionRecords decline; watches for the SWE's own fix and verifies it

Unanswered → bounded retry → escalate to backup. Answering is not approval.

5 · Execute & verify

Before acting

  • Re-run probes & config check
  • Approval bound to action, incident, responder, expiry
  • One mutation per action — retries are no-ops

Verification

  • ≥ 10 successful synthetic checkouts
  • Spanning ≥ 30 seconds
  • ≥ 10 successful Sentry checkout traces

If it fails

  • No automatic retry
  • Escalate to backup
  • Never reported as "resolved"

SWE fixed it themselves? The backend detects the config change and runs the same verification.

6 · Closing the loop

After verified recovery

  • System drafts a suggested incidents.md row: symptom, evidence at the time, fix, outcome, follow-up
  • Shown on the dashboard / in the retrospective
  • SWE edits and commits it — the file stays human-curated

Why a markdown file

  • Readable and reviewable in a PR
  • SWE controls what the agent learns from
  • Bad lessons are deleted with a line edit
  • No hidden state shaping recommendations

Demo story

Incident A

Recommendations time out. No precedent. Agent proposes disable recommendations. SWE approves by phone. Verified recovered. SWE adds INC-7.

Incident B

Same symptom, but payment probe is slow. INC-7 is similar — but the gate blocks disabling recommendations. SWE declines, switches provider. Detected and verified. SWE adds INC-9.

Incident C

Same masked pattern returns. Context agent surfaces INC-9 first. Agent recommends switch payment provider, citing INC-9. One phone "yes" → recovered.

Each fix makes the next recommendation better — and a human stays in control of every change.
